> [!KEY] Agent 是「會自己用工具、反覆嘗試直到完成任務」的 AI；而 `AGENTS.md`／`CLAUDE.md` 是寫給它看的**專案說明書**，讓它每次都照同一套規則做事。

## 這講在學什麼

前幾講都是「問一句、答一句」的生成。這一講往實務走：當 AI 能讀檔案、執行指令、修改程式碼時，它就從「聊天機器人」變成能幫你做事的 **Agent**。問題也隨之而來——它怎麼知道你的專案要怎麼做？答案就是一份好的規則文件。

> [!NOTE] 這個網站本身就是這一講的作業成果：整個網站都是依照 repo 裡的 `AGENTS.md` 規則產生的。

## Agent = 模型 + 執行框架

| 元件 | 角色 | 比喻 |
|---|---|---|
| 模型（Model） | 思考、決定下一步 | 大腦 |
| 工具（Tools） | 讀寫檔案、跑指令、搜尋網路 | 手腳 |
| 執行框架（Harness） | 把模型的決定交給工具執行，再把結果回饋給模型 | 神經系統 |

Agent 的運作是一個迴圈：

```text
目標 → 模型思考 → 呼叫工具 → 看結果 → 再思考 → …… → 完成
```

> [!EXAMPLE] 請 Agent「新增一篇第 5 講的筆記」：它會先讀規則文件、看範本、建立檔案、寫內容、執行檢查腳本；腳本報錯就自己修，直到通過為止。

## 為什麼需要 AGENTS.md

Agent 每次開新對話都是「失憶」的：它不知道你的命名習慣、資料夾結構、不能碰哪些檔案。`AGENTS.md`（或 Claude Code 讀的 `CLAUDE.md`）放在專案根目錄，Agent 一開始就會讀進**上下文**（Context）。

| | Vibe Coding | 規則驅動（AGENTS.md） |
|---|---|---|
| 目標 | 把這一頁做出來 | 建立能持續產出的系統 |
| 規則在哪 | 散落在每次的 prompt 裡 | 寫成文件，跟著專案走 |
| 第 10 頁和第 1 頁 | 風格可能漂移 | 格式、風格一致 |
| 換人／換 AI | 要重新解釋 | 讀文件就能接手 |

> [!TIP] `CLAUDE.md` 可以用 `@AGENTS.md` 匯入另一份檔案。本專案就是這樣做：規則只寫一份在 `AGENTS.md`，各家 AI 工具共用。

## 一份好規則文件該寫什麼

1. **目的與讀者**：這專案是什麼、給誰看。
2. **技術約束**：能用／不能用的框架、套件。
3. **目錄結構**：每個檔案放哪、做什麼。
4. **新增內容的步驟**：一步一步，像食譜。
5. **格式與命名規則**：最好附範本。
6. **驗證方式**：一個指令就能檢查對不對。
7. **權限邊界**：哪些可以直接做、哪些要先問、哪些禁止。

> [!WARNING] 規則寫得模糊，AI 就會「自由發揮」。「保持風格一致」不夠具體；「顏色只能用 `:root` 裡定義的 CSS 變數」才是 AI 能遵守的規則。能用腳本檢查的規則，就寫成腳本。

## 重點整理

- Agent = 模型 + 工具 + 執行框架，以迴圈方式反覆執行直到完成任務。
- Agent 每次都從零開始，需要一份放在專案裡的規則文件提供上下文。
- AGENTS.md 的價值在於「可重複」：讓第 N 次產出和第 1 次一樣符合規範。
- 好規則要具體、可驗證，並明確寫出權限邊界。

## 自我檢測

<details>
<summary>Q1. 「Harness」在 Agent 中負責什麼？</summary>

負責執行迴圈：把模型決定要呼叫的工具真的執行，再把執行結果送回模型，讓它決定下一步。

</details>

<details>
<summary>Q2. 「頁面要好看」為什麼不是一條好規則？</summary>

太模糊，無法判斷有沒有做到，AI 只能自行詮釋。好規則應該具體、可檢查，例如指定配色變數、字型、版面寬度。

</details>

<details>
<summary>Q3. 為什麼本專案要寫一支 build.mjs 檢查腳本？</summary>

讓規則可以被自動驗證。Agent 新增筆記後執行腳本，有錯就會看到明確的錯誤訊息並自行修正，不必靠人工檢查格式。

</details>
